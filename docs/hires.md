# Hi-Res 音质：使用、实现与验证

Lilt 支持请求 QQ 音乐的 Hi-Res FLAC 音源：设置页选项显示为 **Hi-Res（FLAC）**，播放页徽标显示为 **Hi-Res**，代码与配置中的对应值为 `hires`。

本文说明当前仓库的实现行为。接口探测与完整解码测试的运行方式见 [Hi-Res 测试指南](hires-probe.md)；音频设备切频与输出策略见 [桌面音频输出说明](desktop-audio.md)。

## 如何使用

1. 在 Lilt 中使用 QQ 或微信扫码登录。
2. 打开「设置 → 音质」，选择 **Hi-Res（FLAC）**。
3. 播放下一首歌曲。修改音质设置不会中断或重新加载当前正在播放的歌曲。
4. 在「正在播放」页面查看进度条下方的音质徽标，确认实际使用的音源。

账号需具备对应歌曲及音质的收听权限，且歌曲本身提供该音源。微信扫码登录可直接使用，无需额外提取浏览器 Cookie 或手动输入令牌。未登录时，在线请求仅尝试 QQ 音乐允许匿名播放的标准音质；已有缓存仍按缓存复用策略读取。

### 设置与实际播放音质

音质设置表示优先请求的档位，而播放页徽标反映实际取得的音质。选择 Hi-Res 后，若上游未提供该档位，播放器会自动尝试较低档位。

| 音质选项 | 配置值 | 音源前缀 | 格式 | 播放页标识 |
| --- | --- | --- | --- | --- |
| 标准（128k） | `standard` | `M500` | MP3 | 不显示音质徽标 |
| 极高（320k） | `exhigh` | `M800` | MP3 | 不显示音质徽标 |
| 无损（FLAC） | `lossless` | `F000` | FLAC | 无损 |
| Hi-Res（FLAC） | `hires` | `RS01` | FLAC | Hi-Res |

FLAC 文件同样存在不同的位深与采样率规格。当前实现会严格区分 `F000` 与 `RS01` 档位，并校验 `RS01` 文件头，不会仅凭 `.flac` 扩展名或用户设置就显示 Hi-Res。

## 音源获取与自动降级

Lilt 直连 QQ 音乐服务，复用现有的播放地址接口，并通过文件名前缀指定音质档位：

| 项目 | 当前实现 |
| --- | --- |
| 网关 | `https://u.y.qq.com/cgi-bin/musicu.fcg` |
| Hi-Res 模块 / 方法 | `vkey.GetVkeyServer` / `CgiGetVkey` |
| 请求文件名 | `RS01` + 歌曲 MID + media MID + `.flac` |
| 登录参数 | 使用当前会话的音乐账号 ID、MusicKey、登录类型及已有设备字段 |
| 微信鉴权 | 保留 `tmeLoginType=1`，由现有会话逻辑填充 `comm` |

获取播放地址后，播放器会发送 `Range: bytes=0-65535` 请求，最多读取前 64 KiB 用于探测。即使 CDN 忽略 `Range` 并返回完整文件，应用也会限制读取量并及时关闭响应。校验内容包括：

- 返回路径对应 `RS01`，且响应内容为可解析的普通 FLAC 文件。
- FLAC `STREAMINFO` 中的位深至少为 24-bit，采样率至少为 44.1 kHz。
- 能够跳过文件头之前的有效 `ID3` 标签，并正确读取 `STREAMINFO`。

上述位深与采样率阈值仅作为本项目对 `RS01` 候选的准入条件，既不表示每首歌曲都固定为 24-bit / 96 kHz，也不代表对输出设备的规格认证。

Hi-Res 的自动降级顺序为：

```text
RS01 Hi-Res FLAC → F000 普通无损 FLAC → M800 320k MP3 → M500 128k MP3
```

当 Hi-Res 业务请求被拒绝、返回空链接、路径不匹配、CDN 返回 403/404/416，或文件头无效、规格未满足准入条件时，播放器会继续尝试较低档位。网络连接错误、超时及其他未归类为资源不可用的异常会作为播放错误返回，而不会当作账号缺少 Hi-Res 权限。普通无损与 MP3 沿用既有请求逻辑；如果所有候选均未提供可用地址，则报告歌曲不可用。上述降级发生在播放地址获取与文件头探测阶段；通过探测后的正式下载或解码失败，目前不会再次触发音质降级。

降级后，播放流的 `Level`、格式与文件大小均对应实际选中的候选档位。例如，当 Hi-Res 不可用但普通无损可用时，徽标会显示为「无损」。音质徽标由 UI 文字与圆角边框直接绘制，不依赖位图或 SVG 资源。

## 文件大小、缓存与解码

歌曲模型中的 `SizeHiRes` 读取自上游 `file.size_hires`，保存到队列时使用 JSON 字段 `sizeHiRes`，搜索结果补全流程也会保留该字段。若旧队列缺失此值，请求 Hi-Res 前会自动补查歌曲详情。

如果探测响应中能够读取到完整资源大小，则优先采用该大小（HTTP 206 读取 `Content-Range` 的总长度，HTTP 200 使用 `Content-Length`）；否则使用歌曲元数据中的 `size_hires`，避免将探测响应的局部长度误当作整首歌曲的大小。

文件大小未知时，Hi-Res 仍按已解码的音频时长判断何时开始或恢复播放。相关阈值与进度条行为见 [流式播放缓冲](playback-buffering.md)。

缓存按歌曲 ID 与实际音质隔离存储，例如：

```text
<id>-hires.flac     <id>-hires.json
<id>-lossless.flac  <id>-lossless.json
```

请求 Hi-Res 时不会直接命中普通无损缓存，降级取得的普通无损也不会被保存为 `hires`。现有缓存策略允许较低音质请求复用较高音质缓存，此时播放徽标仍按缓存中的实际音质显示。

Hi-Res 沿用现有的 FLAC 解码器，按文件中的采样率与位深进行解码。当 `STREAMINFO` 提供非零样本总数时，解码器在读完这些样本后结束，避免把尾部标签误当作新的音频帧。目前已验证完整解码、流式读取时拖动进度，以及缓存重播下的拖动与解码。

缓存遵循设置中的容量限制；当缓存关闭，或单曲体积超过缓存总上限的四分之一时，不会长期保留该文件。Hi-Res 音源通常更大，测试样例体积约为 81 MB。

### 音源规格与设备输出

「Hi-Res」徽标描述的是客户端取得的音源档位。音频后端虽已具备跟随主音源采样率打开设备的机制，但最终输出仍取决于系统音频服务、硬件设备及后端协商结果。

取得 24-bit / 96 kHz FLAC、成功解码与声卡最终以何种格式输出，分属不同的验证层次。自动解码测试不会向声卡播放声音，也不验证端到端逐位一致的输出；输出机制与平台说明见 [桌面音频输出说明](desktop-audio.md)。

## 已完成的验证

2026-11-15，在 Linux x86_64、Lilt 0.4.4 的微信登录会话下完成了以下验证：

| 验证项 | 结果与范围 |
| --- | --- |
| 接口与实际文件头 | `CgiGetVkey` 成功返回 `RS01`（24-bit / 96 kHz / 双声道）；同曲 `F000` 对照为 24-bit / 48 kHz |
| 完整应用解码链路 | 数字歌曲 ID `491303214`、MID `001NJ5rE2EPEIv`，完整解码 42,073,044 个交错声道样本，拖动进度及 Hi-Res 缓存重播均通过 |
| 降级与元数据回归 | 覆盖权限拒绝、空地址、CDN 403/404、无效音频及规格不足场景；确认实际音质与文件大小一致 |
| 设置与缓存回归 | 覆盖 `hires` 的选择与保存、旧队列恢复、搜索元数据保留、缓存隔离及实际音质徽标展示，均通过 |
| 实际界面播放 | 用户实机确认 Hi-Res 播放正常；另确认暂停约 3 分钟后恢复播放，歌词显示正常 |

以上结果仅针对测试时的账号、歌曲与环境，不代表所有歌曲均提供 Hi-Res。样例歌曲后续的权限或资源变化不会影响本地回归测试，但可能影响在线测试结果。

### 复测与问题定位

- **选择了 Hi-Res，但未显示对应徽标**：请先播放下一首再检查实际播放档位；或换一首在官方客户端中确认支持且当前账号可收听的歌曲。修改设置不会立即替换当前播放流。
- **显示「无损」**：可能已自动降级为普通 FLAC；请保留设置，按 [Hi-Res 测试指南](hires-probe.md) 对该歌曲做独立探测。
- **探测成功但播放失败**：文件头探测不能替代完整解码测试，请继续运行 `TestLiveHiResPlayback`。
- **能正常播放但未留下缓存**：检查缓存是否关闭、容量及单曲大小限制；只有完整下载结束的文件才会转为完整缓存。
- **修改输出设备或系统采样率后存在疑问**：对照 [桌面音频输出说明](desktop-audio.md) 检查实际输出，不能仅凭音源徽标判断声卡规格。

测试命令、正式版与开发版的会话读取方式，以及如何分享不含令牌的诊断输出，统一维护在 [Hi-Res 测试指南](hires-probe.md)。
